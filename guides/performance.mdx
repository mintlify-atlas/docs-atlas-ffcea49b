## Performance Targets

From README.md:246-253, cc-statusline is designed for minimal performance impact:

| Metric | Target | Typical |
|--------|--------|---------|
| **Execution Time** | &lt;100ms | 45-80ms |
| **Memory Usage** | &lt;5MB | ~2MB |
| **CPU Impact** | Negligible | &lt;1% |
| **Dependencies** | Minimal | jq only |

<Info>Benchmarked on macOS with all features enabled</Info>

## Performance Impact by Feature

### Zero-Cost Features

These features have negligible performance impact (&lt;5ms):

<AccordionGroup>
  <Accordion title="📁 Working Directory" icon="folder">
    **Impact:** ~1ms
    
    **Why fast:** Simple environment variable lookup and string replacement
    
    ```bash
    current_dir=$(pwd | sed "s|^$HOME|~|g")
    ```
  </Accordion>
  
  <Accordion title="🤖 Model Name" icon="robot">
    **Impact:** ~2ms
    
    **Why fast:** Direct JSON field extraction
    
    With jq:
    ```bash
    model_name=$(echo "$input" | jq -r '.model.display_name')
    ```
  </Accordion>
  
  <Accordion title="🎨 Colors & Emojis" icon="palette">
    **Impact:** &lt;1ms
    
    **Why fast:** Simple string concatenation
    
    Colors are ANSI escape codes - no computation needed.
  </Accordion>
</AccordionGroup>

### Low-Cost Features

These features add minimal overhead (5-20ms):

<AccordionGroup>
  <Accordion title="🌿 Git Branch" icon="code-branch">
    **Impact:** ~10ms
    
    **Why reasonably fast:** Single git command with caching
    
    ```bash
    git_branch=$(git symbolic-ref --short HEAD 2>/dev/null)
    ```
    
    <Tip>Git operations are cached by the OS. Subsequent calls are faster.</Tip>
  </Accordion>
  
  <Accordion title="🧠 Context Remaining" icon="brain">
    **Impact:** ~5ms with jq, ~15ms without
    
    **Why fast:** Simple arithmetic on JSON fields
    
    From bash-generator.ts:164-198:
    ```bash
    CONTEXT_SIZE=$(echo "$input" | jq -r '.context_window.context_window_size')
    CURRENT_TOKENS=$(echo "$USAGE" | jq '(.input_tokens // 0) + (.cache_creation_input_tokens // 0)')
    context_remaining_pct=$(( 100 - (CURRENT_TOKENS * 100 / CONTEXT_SIZE) ))
    ```
  </Accordion>
</AccordionGroup>

### Medium-Cost Features

These features can add noticeable overhead (20-100ms):

<AccordionGroup>
  <Accordion title="💵 Usage & Cost" icon="dollar-sign">
    **Impact:** ~50-200ms
    
    **Why slower:** Requires spawning ccusage process
    
    ```bash
    npx ccusage@latest
    ```
    
    <Warning>This is the single most expensive operation. Can add 100-500ms if ccusage cache is cold.</Warning>
    
    **Optimization:** ccusage includes file-based locking to prevent concurrent execution:
    
    From README.md:278-305 (locking mechanism tests):
    ```bash
    # Only 1 process runs ccusage at a time
    # Others skip gracefully
    ```
  </Accordion>
  
  <Accordion title="📊 Token Statistics" icon="chart-bar">
    **Impact:** ~10-30ms
    
    **Why slower:** Requires parsing large usage data from ccusage
    
    Depends on ccusage call + additional jq parsing.
  </Accordion>
  
  <Accordion title="⚡ Burn Rate" icon="fire">
    **Impact:** ~5-15ms
    
    **Why slower:** Additional calculations on usage data
    
    Requires ccusage data + burn rate calculation.
  </Accordion>
  
  <Accordion title="⌛ Session Reset Time" icon="clock">
    **Impact:** ~20-40ms
    
    **Why slower:** Time zone calculations and formatting
    
    Requires ccusage + date/time arithmetic + progress bar rendering.
  </Accordion>
</AccordionGroup>

## Optimization Strategies

### Strategy 1: Minimal Configuration

For maximum speed, use only essential features:

```bash
cc-statusline init
# Select only:
# ✓ 📁 Working Directory
# ✓ 🌿 Git Branch
# ✓ 🤖 Model Name
# ✓ 🧠 Context Remaining
# ✗ All usage/cost features
```

**Expected performance:** 20-40ms

### Strategy 2: Disable ccusage

ccusage is the slowest component. If you don't need cost tracking:

```bash
cc-statusline init
# Deselect:
# ✗ 💵 Usage & Cost
# ✗ 📊 Token Statistics  
# ✗ ⚡ Burn Rate
# ✗ ⌛ Session Reset Time
```

**Expected improvement:** -100 to -500ms

### Strategy 3: Install jq

The bash fallback parser is slower than jq:

<CodeGroup>
```bash macOS
brew install jq
```

```bash Linux
sudo apt-get install jq
```
</CodeGroup>

**Expected improvement:** -10 to -30ms for JSON parsing

From README.md:42:
> ⚠️ Basic fallback parser is used (less reliable)

### Strategy 4: Disable Logging

Debug logging adds I/O overhead:

```bash
cc-statusline init
# Select "No" for debug logging
```

**Expected improvement:** -5 to -10ms

From bash-generator.ts:64-84, logging includes:
- File I/O to .claude/statusline.log
- JSON formatting
- Multiple echo statements

### Strategy 5: Use Compact Theme

Progress bars and formatting add rendering time:

```bash
cc-statusline init
# This is not exposed in prompts yet, but you can edit the generated script
# Look for progress_bar() function calls and simplify
```

**Expected improvement:** -2 to -5ms

## Technical Optimizations

### Bash Script Optimization

The generated bash script is already optimized:

<AccordionGroup>
  <Accordion title="Single Pass JSON Parsing" icon="gauge">
    All JSON fields are extracted in one pass to avoid multiple jq invocations.
    
    From bash-generator.ts:127-133:
    ```bash
    if [ "$HAS_JQ" -eq 1 ]; then
      current_dir=$(echo "$input" | jq -r '.workspace.current_dir')
      model_name=$(echo "$input" | jq -r '.model.display_name')  
      model_version=$(echo "$input" | jq -r '.model.version')
      # All extracted in one conditional block
    fi
    ```
  </Accordion>
  
  <Accordion title="Conditional Feature Execution" icon="code-branch">
    Features are only executed if enabled during generation.
    
    From bash-generator.ts:9-14:
    ```typescript
    const hasGit = config.features.includes('git')
    const hasUsage = config.features.some(f => ['usage', 'session', 'tokens', 'burnrate'].includes(f))
    
    // Only generate code for enabled features
    ${hasGit ? generateGitBashCode(gitConfig, config.colors) : ''}
    ```
  </Accordion>
  
  <Accordion title="Graceful Fallbacks" icon="shield">
    Missing dependencies don't cause errors or retries.
    
    ```bash
    if command -v jq >/dev/null 2>&1; then
      HAS_JQ=1
    else
      HAS_JQ=0
      # Use bash fallback
    fi
    ```
  </Accordion>
  
  <Accordion title="Minimal Subshells" icon="terminal">
    Command substitution is minimized to reduce process spawning.
  </Accordion>
</AccordionGroup>

### ccusage Locking Mechanism

From README.md:278-305, cc-statusline prevents performance issues from concurrent ccusage calls:

```bash
# File-based locking ensures only 1 ccusage process at a time
# Other statusline updates skip usage data gracefully
```

**Benefits:**
- Prevents process pile-up
- No hanging processes
- Automatic lock cleanup

**Test the locking:**
```bash
# Spawn 10 concurrent statusline processes
for i in {1..10}; do 
  echo '{}' | .claude/statusline.sh & 
done

# Verify only 1 ccusage runs
ps aux | grep ccusage
```

## Monitoring Performance

### Enable Performance Logging

Add timing to your statusline:

```bash
# Edit .claude/statusline.sh manually
# Add at the top:
START_TIME=$(date +%s%N)

# Add at the end:
END_TIME=$(date +%s%N)
ELAPSED=$(( (END_TIME - START_TIME) / 1000000 ))
echo "[Performance: ${ELAPSED}ms]" >> .claude/statusline-perf.log
```

### Analyze Performance Logs

```bash
# View performance history
cat .claude/statusline-perf.log

# Calculate average
awk -F'[' '{print $2}' .claude/statusline-perf.log | \
  awk -F'ms' '{sum+=$1; count++} END {print "Average: " sum/count "ms"}'
```

## Troubleshooting Slow Performance

<Steps>
  <Step title="Identify the Bottleneck">
    Enable debug logging and check which features are taking time:
    
    ```bash
    # Edit .claude/statusline.sh
    # Add time stamps around each feature
    echo "[$(date +%s%N)] Starting git branch" >> .claude/statusline.log
    git_branch=$(git symbolic-ref --short HEAD 2>/dev/null)
    echo "[$(date +%s%N)] Completed git branch" >> .claude/statusline.log
    ```
  </Step>
  
  <Step title="Check ccusage Performance">
    Test ccusage directly:
    
    ```bash
    time npx ccusage@latest
    ```
    
    If this takes &gt;500ms, ccusage is the bottleneck.
  </Step>
  
  <Step title="Verify jq Installation">
    ```bash
    time echo '{}' | jq .
    ```
    
    Should be &lt;10ms. If slower, reinstall jq.
  </Step>
  
  <Step title="Check Disk I/O">
    If logging is enabled:
    
    ```bash
    # Disable logging and compare
    cc-statusline init
    # Select "No" for logging
    ```
  </Step>
</Steps>

## Performance FAQ

<AccordionGroup>
  <Accordion title="Why is first run slow?" icon="question">
    **Answer:** OS disk caching, ccusage cache warming, and npm package loading.
    
    Subsequent runs are much faster due to caching.
  </Accordion>
  
  <Accordion title="Does statusline slow down Claude Code?" icon="question">
    **Answer:** No, statusline runs asynchronously and doesn't block user input.
    
    Even a 500ms statusline won't impact your ability to type or interact with Claude Code.
  </Accordion>
  
  <Accordion title="Can I make it update less frequently?" icon="question">
    **Answer:** Statusline update frequency is controlled by Claude Code, not cc-statusline.
    
    Typically updates on each command completion.
  </Accordion>
  
  <Accordion title="Does colors/emojis slow it down?" icon="question">
    **Answer:** No, ANSI escape codes have negligible performance impact (&lt;1ms).
    
    Disabling colors won't improve performance noticeably.
  </Accordion>
</AccordionGroup>
